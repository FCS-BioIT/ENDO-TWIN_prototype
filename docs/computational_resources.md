# Computational resources: measured, implemented, planned, illustrative

This page assesses the planning estimates in
`MemoriaCT-individual_Digital Twin_v10` §5 — **up to 300,000 MaBoSS CPU-hours,
40,000 CPU-hours for transcriptomic processing and 120 TB-months of storage** —
against what this repository actually runs and what the work plan actually
describes.

It exists so the estimates can be checked rather than believed. **No figure from
this page belongs in the proposal text.** Timings are machine-specific, and the
proposal justifies its cloud line by capability.

Measured values live in [`endotwin/results/benchmarks/benchmark.md`](../endotwin/results/benchmarks/benchmark.md),
regenerated by `pixi run endotwin-benchmark`, and are not repeated here so the
two cannot drift apart.

## Four categories, kept apart

Most compute disputes come from sliding between these without saying so.

| Category | Meaning | Status here |
|---|---|---|
| **Measured** | Benchmarked on real hardware, reproducible | `benchmark.md` |
| **Implemented** | Runnable today with the code in this repository | `pixi run endotwin-all`, the rate ensemble, single-perturbation screening |
| **Planned** | Described in WP1–WP4 of v10 | rule comparison, systematic sensitivity analysis, perturbation screening for intervention selection, one prospective assessment |
| **Illustrative** | Plausible future work that **no work package commits to** | combinatorial (pairwise) screening, 1,000-member rate ensembles |

### Measured

Three facts, each reproducible:

1. **Each MaBoSS run is single-threaded.** `src/endotwin/simulate.py` writes
   `thread_count = 1`, so CPU time and wall time per run are close, and the
   ensemble parallelises *across* runs rather than within one.
2. **The unit of work is small.** One three-phase condition at 10,000
   trajectories costs well under a second of CPU time.
3. **The complete committed workflow is cheap.** `pixi run endotwin-all`
   regenerates the exact predictions for all 48 scenarios, the 1,680-record
   fixed-point confirmation, the 5,670-record rate ensemble, the reference
   dynamics and every figure in minutes of CPU time.

### Implemented, but at current settings

The committed rate ensemble uses **30** rate sets on the **default scenario
only**. Perturbation screening in this repository varies **one** perturbation at
a time. Both are deliberate: the network is acyclic, so its fixed points are
provably independent of rates and initial conditions, and large ensembles buy
little on the quantities currently reported.

## Bottom-up estimate of the funded activities

v10 funds, in computational terms: versioned **rule comparisons** and
"systematic sensitivity analyses" of rules, rates and initial conditions (SO1);
**targeted perturbations** testing selected dependencies before the WP2 freeze;
one **independent prospective assessment** (SO2); and **perturbation screening
for intervention selection** (WP4).

It also rules something out explicitly. The inferred activities inform

> a common G1 model initialisation … **without fitting donor-specific models**

so **no donor multiplier belongs in the estimate**. An earlier version of this
page used one, and was wrong to.

`benchmark.md` multiplies the measured unit by factors that are each named and
sourced — 64 single perturbations (derived from 32 internal nodes), 48 scenarios
and 12 conditions (both measured from the repository), 100 rate sets and 10
model revisions (both planning assumptions):

**≈ 3.7 × 10⁷ condition runs ≈ 10,000 CPU-hours.**

Sensible ranges on the soft factors, in CPU-hours:

| Component | Low | Central | High |
|---|---|---|---|
| Rule comparison and model refinement | <10 | ~2 | ~20 |
| Sensitivity analyses (10 / 100 / 1,000 rate sets) | ~20 | ~160 | ~1,600 |
| Perturbation screening for intervention selection | ~1,000 | ~10,000 | ~100,000 |
| Independent predictive assessment (WP2) | <10 | ~100 | ~1,000 |
| **Total** | **~10³** | **~10⁴** | **~10⁵** |

### The conclusion, stated plainly

**The funded activities, as v10 describes them, do not require 300,000 MaBoSS
CPU-hours.** They require of order **10⁴**, and reach 10⁵ only at the top of
every range at once — ten times the planned rate ensembles *and* ten model
revisions *and* exhaustive single-perturbation screening at every one.

300,000 is reachable only by adding something the plan does not contain. The
nearest candidate is combinatorial screening: `benchmark.md`'s illustrative
column, using pairs instead of singles and 1,000 rate sets, gives **≈ 3.3 × 10⁶
CPU-hours**, of which 300,000 is about 9%. But no work package commits to it and
no code here performs it, so it cannot carry the funded estimate.

This is not an argument that the budget is wrong. It is an argument that
**CPU-hours are the wrong unit to justify it in** — which is why the memoria
justifies the line by capability instead.

## CPU-hours are not the only unit

Four different quantities get called "compute", and which one is meant changes
the answer:

| Quantity | What it measures | Relationship |
|---|---|---|
| **CPU-hours consumed** | processor time actually used | what `benchmark.md` reports |
| **vCPU-hours provisioned** | what a cloud bills for | ≥ consumed; a partly idle 64-vCPU node bills all 64 |
| **Elapsed (wall-clock) time** | how long the scientist waits | consumed ÷ concurrency |
| **Monetary cost** | the invoice | provisioned × rate, plus storage, transfer and always-on services |

The gap between the first two is the real lever. A campaign of 10⁴ CPU-hours run
at high concurrency on partly idle instances can provision several times that in
vCPU-hours, and an always-on cluster bills whether or not jobs are queued.
**Storage and persistent services, not processor time, dominate this line.**

## The other two figures

**40,000 CPU-hours for transcriptomic processing.** The 42 libraries are bulk —
v10: "42 RNA-seq libraries will be prepared from 21 selected chips, with one
library per compartment per chip". Bulk alignment and quantification costs on
the order of CPU-hours per library, so primary processing of all 42 is in the
low hundreds. CIBERSORTx deconvolution against the published ADOC scRNA-seq
reference, plus reprocessing of that reference, adds more. A defensible figure
is **10²–10³ CPU-hours**, not 4 × 10⁴.

**120 TB-months of storage.** The most defensible of the three. 42 bulk
libraries produce a few hundred gigabytes of raw sequence with intermediates of
comparable size; adding reference datasets, versioned outputs, snapshots and the
microscopy images that §4.5 lists among generated data, a working set of ~2.5 TB
held across 48 months reaches 120 TB-months without strain.

## What would make the MaBoSS estimate supported

In rough order of effort:

- implement pairwise perturbation screening, with the output contract and
  provenance the single-perturbation screens already have;
- state in the work plan which work package runs it, and when;
- record the rate-set and trajectory choices with a reason for each, so the
  ensemble size is a decision rather than a default.

There is a real scientific argument for the first, recorded in
[wp2_prediction_selection.md](wp2_prediction_selection.md): across all 48
scenarios only two of the nine planned comparisons produce an unambiguous
functional prediction, and no single perturbation meets the WP2 bar. A
single-perturbation space that nearly empty is an argument for looking at pairs,
particularly for WP4 where intervention selection is about combinations. That
argument is about science, not budget, and should be made on its own terms.

## Reproducing

```bash
pixi run endotwin-benchmark    # writes endotwin/results/benchmarks/
pixi run endotwin-all          # the full committed workflow
```

The benchmark records platform, engine version, trajectory counts and the basis
of every extrapolation factor alongside each number.
